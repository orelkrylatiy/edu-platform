# SA Practice Lab

Связано: [[Middle System Analyst Roadmap]] · [[SA Interview Scorecard]].

Не делать огромную систему и не писать React-интерфейс. На интервью важнее решить задачу с чистого листа. Один сквозной кейс используется для обучения, остальные — для проверки переноса навыка. Артефакты делаются самостоятельно в Markdown, PlantUML, BPMN.io, OpenAPI и SQL. Числа и ограничения ниже учебные.

## Диагностика без подготовки

**Это не экзамен.** Цель — понять, что уже знакомо из разработки, а что предстоит изучать с нуля. Не надо знать терминологию заранее. В день 01 достаточно черновых ответов, не нужны диаграммы в редакторе, код, настройка БД или поиск готовых решений.

Порядок: 2–3 минуты попробовать самостоятельно → записать исходный уровень → при необходимости открыть подсказку и подумать ещё 1–2 минуты → перейти дальше. Максимум 20–30 минут на все шесть задач. Если совершенно не знаешь, сразу отметь 0 и двигайся дальше. Не изучай весь раздел ради диагностики.

Шкала из [[SA Interview Scorecard]]: 0 — не знаю; 1 — узнаю термин; 2 — могу объяснить с примером; 3 — самостоятельно применяю в незнакомой задаче; 4 — могу защитить альтернативы и ограничения. Оценивай знания **до подсказки**. Баллы ниже не определяют профессиональный грейд; не завышай оценку после чтения.

<details>
<summary>Подсказка после попытки</summary>

<details>
<summary>Подсказка после попытки</summary>

## Сквозной кейс: Order Management

Запрос бизнеса: «Хотим, чтобы покупатель мог оформить заказ и оплатить онлайн, а склад и клиент узнавали статус». Это единственное исходное согласованное условие; всё остальное нужно выяснить. Наставник играет заказчика и не сообщает ответы заранее.

### A. Requirements
Спросить: кто акторы, что входит в MVP, кто владеет остатками, когда резерв, сколько действует, как отменять, возможна ли повторная/частичная оплата, какие ошибки/права/нагрузка. Фиксировать предположения отдельно.
Результат: scope, 8–12 FR с ID, 3–5 измеримых NFR с условиями, 4–6 бизнес-правил, Use Case создания и оплаты заказа с ветками, 6 Given/When/Then.
Проверка: требования атомарны, проверяемы, непротиворечивы; нет придуманного согласования; исключения включают отсутствие товара, отказ и неизвестный результат платежа. Дополнительный конфликт: бизнес хочет держать резерв 30 минут, склад — 5 минут. Выяснить цели, предложить варианты, зафиксировать решение владельца и нерешённые вопросы.

### B. API
Спроектировать create/get/list/cancel заказа и создание попытки оплаты. Выбрать URI, методы, статусы, types/required/nullability, error schema, пагинацию, авторизацию, idempotency key и поведение при повторе с другим payload.
Результат: openapi.yaml + запросы для mock или Postman. Проверить валидатором, затем отдельно объяснить, какие свойства нельзя проверить одним mock.
Проверка: статус заказа не меняется GET, корректное различие 400/401/403/404/409, повтор не приводит к лишней бизнес-операции; согласованность с Use Case.

#### B2. Маппинг и legacy SOAP
Внешний провайдер присылает JSON: `{"payment_ref":"p123","order_ref":"101","amount_minor":12000,"currency":"KZT","result":"OK","paid_at":"2026-02-01T10:00:00+05:00"}`. Внутренний контракт: `paymentId`, `orderId` (integer), `amount` (decimal string, две дробные цифры для KZT), `currency`, `status` (SUCCESS/FAILED/PENDING), `occurredAt` (UTC). Согласовать таблицу source path → target path → тип → required/null → преобразование → validation/error. Провайдер гарантирует для KZT 100 minor units на 1 KZT; OK означает SUCCESS, неизвестный код — ошибка маппинга/карантин, не автоматический SUCCESS. Проверить отсутствующее поле, неизвестный статус, некорректный order_ref, повтор payment_ref; объяснить источник истины. Ожидаемые примеры: amount="120.00", orderId=101, occurredAt="2026-02-01T05:00:00Z".

Legacy drill: прочитать SOAP Primer §2.1/2.3, на бумаге обернуть PaymentStatusRequest с paymentRef в SOAP Envelope/Body с namespace, описать успешный ответ и Fault; объяснить роль WSDL и XSD, отличие SOAP от REST, преобразование SOAP-ответа в внутренний JSON. Не требуется разворачивать SOAP-сервис.

### C. Database
Сущности customers, products, orders, order_items, payments. Различить текущую цену и историческую цену покупки. ERD: PK/FK, обязательность, cardinality, правила уникальности. Предложить ограничения, индексы и транзакции; обосновать не только названия.

Мини-датасет для PostgreSQL (не production schema; не моделирует реальное частичное списание или возврат). Сначала самостоятельно спроектировать ERD, затем использовать fixture как независимую тренировочную БД. Вариант локального запуска для уже установленного Docker (не требуется, если есть PostgreSQL):

```sh
export POSTGRES_PASSWORD="$(openssl rand -hex 16)"
docker run --rm --name sa-lab-pg -e POSTGRES_PASSWORD -e POSTGRES_DB=sa_lab -d postgres:18
unset POSTGRES_PASSWORD
docker exec -it sa-lab-pg psql -U postgres -d sa_lab
```

Пример для Bash/WSL с openssl: случайный пароль создаётся локально, не записывается в Git; наружу порты не публикуются. При наличии своего PostgreSQL использовать отдельную пустую учебную БД. Для второй сессии открыть второй терминал и повторить docker exec. Ввести SQL один раз в пустую БД; если ошибся, создать новый чистый учебный экземпляр. Остановить по завершении: docker stop sa-lab-pg (данные контейнера временные). Не менять рабочие базы или контейнеры.

```sql
CREATE TABLE customers(id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE products(id int PRIMARY KEY, name text NOT NULL, stock int NOT NULL CHECK(stock >= 0));
CREATE TABLE orders(id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customers(id), status text NOT NULL, created_at date NOT NULL);
CREATE TABLE order_items(order_id int REFERENCES orders(id), product_id int REFERENCES products(id), qty int NOT NULL CHECK(qty > 0), unit_price numeric(12,2) NOT NULL CHECK(unit_price >= 0), PRIMARY KEY(order_id,product_id));
CREATE TABLE payments(id int PRIMARY KEY, order_id int NOT NULL REFERENCES orders(id), status text NOT NULL, amount numeric(12,2) NOT NULL CHECK(amount > 0));
INSERT INTO customers VALUES (1,'A'),(2,'B'),(3,'C'),(4,'D');
INSERT INTO products VALUES (1,'Phone',1),(2,'Cable',10),(3,'Case',5);
INSERT INTO orders VALUES (101,1,'PAID','2026-01-01'),(102,1,'PENDING','2026-02-02'),(103,2,'PAID','2026-02-03'),(104,4,'CANCELLED','2026-02-04');
INSERT INTO order_items VALUES (101,1,1,100),(101,2,2,10),(102,3,1,20),(103,2,3,10),(104,1,1,100);
INSERT INTO payments VALUES (1,101,'FAILED',120),(2,101,'SUCCESS',120),(3,103,'SUCCESS',30),(4,104,'FAILED',100);
```

Решить без ответов. Задачи ниже — чек-лист самостоятельной практики, а не отдельный план обучения.

- [ ] Клиенты без заказов.
- [ ] Заказы без SUCCESS платежа.
- [ ] Успешно оплаченная сумма по каждому клиенту, включая нулевые.
- [ ] Количество единиц товаров только в PAID заказах.
- [ ] Заказы с более чем одной попыткой оплаты.
- [ ] Последний заказ каждого клиента с заказами, также через ROW_NUMBER с tie-breaker id.
- [ ] Выручка по месяцу заказа на основе успешных платежей.

Проверка автора учебного плана: все 7 наборов результатов совпали при независимом прогоне на SQLite. Это проверка fixture, а не PostgreSQL-specific поведения или конкурентных транзакций.

Дополнительные вопросы: чем WHERE по правой таблице отличается от ON в LEFT JOIN? Почему JOIN order_items и payments может умножить сумму? Что делает COUNT(*) vs COUNT(payment.id)? Как предотвратить двойную успешную оплату при предположении «один успешный платёж на заказ»?
EXPLAIN: предложить индекс под выборку последних заказов клиента (`customer_id, created_at, id`), прочитать план до/после на тестовых данных. На мини-датасете Seq Scan может быть оптимален; не требовать Index Scan любой ценой. Объяснить разницу EXPLAIN и EXPLAIN ANALYZE, последний реально выполняет запрос.
Concurrency: два клиента одновременно покупают Phone. В двух сессиях BEGIN с Read Committed; обе читают stock=1, одна UPDATE stock=0 и COMMIT, вторая записывает вычисленный ранее stock=0 и может считать покупку успешной. Для учебного эксперимента сбросить stock=1 после завершения обеих транзакций. Затем обе выполняют UPDATE products SET stock=stock-1 WHERE id=1 AND stock>0 RETURNING stock; первая COMMIT, вторая после ожидания не получает строк. В реальном решении создавать заказ только при успешном обновлении, в той же транзакции, а при отсутствии строки — rollback/отказ. Проверить остаток и результаты обеих сессий. Объяснить блокировки, rollback и retry. SQL с фиксированным stock=0 здесь намеренно неверный учебный пример, не образец реализации.

### D. Modeling
Sequence: клиент, API, order service/DB, внешний payment provider. alt успех/отказ/timeout, проверка статуса при неопределенном результате. BPMN: покупатель и магазин (отдельные pools, message flow); склад как lane при необходимости, XOR оплаты/отказа, timer истечения резерва. State machine: допустимые переходы, терминальные статусы, отмена/истечение.
Проверка: не смешивать BPMN message flow и sequence flow, не рисовать недопустимые переходы; состояния согласованы с требованиями и БД.

### E. Integration
Определить event contract OrderPaid: eventId, type, orderId, occurredAt, version, amount/currency если необходимо. Ключ по orderId, 3 partitions, 2 независимых consumer groups (уведомления/склад). Как распределятся partitions при 1/3/4 consumer в одной группе? Что будет при crash до/после commit offset? Сравнить с RabbitMQ work queue.
Нарисовать retry/DLQ и дедупликацию (проверка и изменение в одной транзакции); объяснить Outbox между записью состояния и публикацией. Не считать exactly-once гарантией отправки email.
Опционально: локальный Kafka или RabbitMQ по официальному quickstart, отправить 3 сообщения, перезапустить consumer; для RabbitMQ manual ACK — показать redelivery.

### F. Architecture & change
Начать с client → monolith → PostgreSQL → external payment provider. Добавлять broker/cache/сервисы только под обоснованную потребность. Сформулировать 2 альтернативы, ошибки и NFR. Затем change request: частичная оплата. Указать затронутые FR, API, constraints, statuses, events, тесты, миграцию и совместимость.
NFR drill: задать учебные условия нагрузки (например 100 RPS, размер ответа, окружение); написать P95 latency, availability и data freshness с окном измерения, исключениями и способом проверки. C4: границы системы, внешние участники и containers. Security drill: customer A пытается прочитать заказ B через GET /orders/{id}; описать серверную проверку владельца, роли поддержки, безопасный ответ 403/404 по контракту, отсутствие утечки персональных данных в логах; два негативных теста.
Баг: два успешных платежа после timeout. Описать steps/expected/actual; отделить гипотезу root cause от доказанного факта; запросить logs/correlation ID; сформулировать тесты повтора и параллельного запроса. Итог: одна Jira-ready постановка (цель/scope, ссылки на FR/API/ERD, бизнес-правила, ошибки, критерии приёмки, открытые вопросы), матрица 3 требований → тесты. При разборе дефекта указать версию документации и окружение.

## Незнакомые кейсы (не смотреть решения до попытки)

| Кейс | Что сделать | Follow-up |
|---|---|---|
| Карта банкоматов | 3 FR/3 NFR, GET API, data model | Нет геолокации, устарели данные, карта не загружается |
| Бронирование билетов | ERD, create/cancel, sequence | Два покупателя, истечение резерва, неопределённая оплата |
| Денежный перевод | API, транзакция, state machine | Повтор POST, сбой после списания, внешний сервис |
| Уведомления | Kafka vs RabbitMQ, event contract | Повтор, ACK, DLQ, недоступный consumer |
| Смена номера телефона | требования, BPMN, API, acceptance | Нет доступа к старому номеру, аудит, права |

Каждый кейс: уточнить условия, обозначить scope, сделать минимум 2 связанных артефакта, назвать 2 failure paths, защитить одно решение и альтернативу. Не использовать реальные конфиденциальные данные.

## Mock protocol

Практика отдельно от теории: ведущий задаёт один вопрос, не помогает до ответа, задаёт 1–2 follow-up. После теории даёт неизвестный кейс и SQL; кандидат рассуждает вслух. Полный mock (ориентир 60–90 мин): 10 мин опыт, 15–20 мин теория из разных блоков, 15–20 мин SQL, 25–35 мин неизвестный кейс с 2–3 артефактами и изменением условия, 5 мин защита решения. Это гибкий формат, не официальный регламент работодателя. Наставник не берёт финальные кейсы из таблицы выше и заранее не раскрывает ожидаемое решение. Использовать экран/редактор диаграмм как на реальном интервью. Разрешены уточнения к интервьюеру, не готовые решения или поиск. Для финальной проверки интервьюер придумывает новый кейс, не повторяет разобранные примеры дословно. В конце — оценка по [[SA Interview Scorecard]], 1–3 слабых места, исправление и повтор на другой задаче.

Промпт наставнику: «Ты интервьюер Middle System Analyst. Используй блоки roadmap, задавай по одному вопросу. Не подсказывай, пока я не отвечу. Уточняй слабые места. Дай практику на чистом листе, SQL с данными и один кейс отказа. В конце оцени по рубрике и сформулируй только наиболее важные пробелы. Не выдумывай мой коммерческий опыт».
